9. Spring Bean 연결 방식 이해 (2026-07-02)
   - Spring은 Nest처럼 module 파일 없이 패키지 스캔과 Bean 등록으로 연결
   - `@Controller` = HTTP 요청을 받는 Bean
   - `@Service` = 비즈니스 로직을 처리하는 Bean
   - `@Repository` = DB 저장/조회 역할을 하는 Bean
   - `@Configuration` = 설정 클래스를 Spring이 관리하도록 등록하고, @Bean 메서드를 담는 클래스
   - `@Bean` = 설정 클래스 안에서 직접 생성한 객체를 Bean으로 등록
   - Bean끼리는 생성자 주입으로 연결
   - 생성자 주입 = 필요한 객체를 생성할 때 생성자로 받아 연결하는 방식
***** 예시코드 *****

@RequiredArgsConstructor //final 필드를 받는 생성자를 Lombok이 자동 생성
public class AuthService {
    private final UserRepository userRepository; //생성자에 들어갈 의존성을 선언한 필드
   //생성자를 자동으로 만들어 주세요 ~ 의미

    public void signup() {
        userRepository.save(null);
    }
}
******************
   - `final` = 주입받을 의존성이 바뀌지 않게 고정

13. 검증 흐름 세부 정리 (2026-07-09)

17. SignupRequest setter 필요성 확인 (2026-07-11)
   - 일단 `@ModelAttribute`는 form 입력값을 dto에 의존성 주입 -> setter, 생성자등으로 값을 저장해줌 
   - 회원가입 form 제출 시 `@ModelAttribute`가 DTO 값 주입
   - `SignupRequest`에 setter가 없으면 form 값이 DTO에 안 들어가 null로 남을 수 있음
   - null 값 때문에 `@Valid`의 `@NotBlank` 검증에서 400 Bad Request 발생 가능
   - `@Setter` 추가 후 form 값이 정상 주입되고 회원가입 요청 처리 확인
   - 문제 상황 = 값 입력했는데도 검증 실패/400 발생
   - 해결 = DTO 바인딩용 setter 추가로 `@ModelAttribute` 값 주입 가능하게 수정
   - 마찬가지로 로그인 dto도 수정완료

21. JWT 인증 방식 개념 정리 (2026-07-19)
   - JWT = JSON Web Token(Header.Payload.Signature)
   - 로그인 성공 후 서버가 토큰을 발급하고, 이후 요청마다 그 토큰으로 인증하는 방식
   - Access Token은 실제 요청에 쓰는 짧은 수명의 토큰
   - Refresh Token은 Access Token이 만료됐을 때 다시 발급받기 위한 긴 수명의 토큰
   - 세션 방식은 서버가 로그인 상태를 기억하고, JWT 방식은 토큰 자체로 인증을 증명
   - 화면 로그인과 API 인증은 방식이 다를 수 있어서 JWT는 보통 보호 API부터 붙이는 게 자연스러움

22-2. JWT 설정값 분리하기 - 코드에 박지 말고 설정 파일에 적기(이후 클래스로 자동 바인딩, 자바 코드에서 사용) @ConfigurationProperties(prefix = "jwt")
   - JWT에서 필요한 값은 `secret key`, `access token 만료시간`, `refresh token 만료시간`
   - 이런 값은 코드에 직접 쓰지 않고 `application.properties` 또는 `application.yml`에 적어둔다
   - 이유 = 나중에 개발/운영 환경마다 값이 달라질 수 있고, 코드 수정 없이 바꾸기 쉽기 때문
   - `application.properties`는 `key=value` 형식
   - `application.yml`은 들여쓰기로 묶어서 적는 형식
   - 둘 다 역할은 같고, 표현 방식만 다르다
   - 예시:
     - `jwt.secret=...` 비밀키(내가 직접 적어야함 )
     - `jwt.access-token-expiration=1800000` Access Token 유효시간
     - `jwt.refresh-token-expiration=1209600000` Refresh Token 유효시간
   - 정리: 설정 파일에는 바뀔 수 있는 값, 코드에는 로그인/검증/토큰 생성 같은 로직을 둔다
   - JwtProperties.java -> 위의 JWT 설정값을 자바 코드에서 쓸 수 있도록 해줌(클래스로 묶어서 사용)
     application.properties 에 JWT값 적음 -> JwtProperties.java에서 읽음 -> JwtUtil / TokenProvider가 받아서 토큰 생성

   - 하는 일: 토큰 생성, 토큰 검증, 토큰의 정보 조회&사용 등
   - 회원가입이나 로그인 자체를 결정하는 곳이 아님(AuthService 역할) -> 성공한 경우 토큰을 만들고 관리하는 곳
   - 아주 쉽게 역할 구분  
     AuthService = 로그인 성공 여부 판단하는 사람 🐯
     JwtTokenProvider = 토큰 만드는 사람 🦊
     JwtFilter = 토큰 검사하는 사람 🐶
     SecurityConfig = 이 사람들을 어디에 연결할지 정하는 사람 🐱
     * SecurutyConfig: 홈화면, 로그인, 회원가입은 토큰이 없어도 접근이 가능해야함, 그 이외는 로그인 필요
   - @Component (가장 기본적으로 bean으로 만드는 어노테이션)
      ├── @Controller
      ├── @RestController
      ├── @Service
      ├── @Repository
      └── @Configuration - @Bean이 붙은 함수가 반환하는 객체도 bean이 된다.
   - JWT의 Payload 구조 (Header.Payload.Signature)
      subject: "1"
      email: "test@test.com"
      role: "USER"
      tokenType: "access"
      issuedAt: 지금 시간
      expiration: 1시간 뒤
      .claim으로 하면 payload에 새로운 정보를 넣을 수 있다. (기본 정보는 메소드가 따로 있음 ex .subject)
   - AccessToken은 유지기간이 짧으며 사용자가 동작시 직접적으로 확인하는 토큰이고
     RefreshToken은 유지기간이 길고 AccessToken의 기간이 만료한 경우 새로 AccessToken을 발급받기 위해 쓰인다.
     RefreshToken의 기간이 만료되었다면 다시 로그인 해야 한다.
     굳이 왜 나눠놓았을까? -> Refresh Token은 너무 강한 권한이라 자주 들고 다니면 위험하기 때문
   - Header: signWith(secretKey)를 보고 JJWT가 자동 생성
     Payload: subject(), issuedAt(), expiration(), claim()으로 직접 채움
     Signature: signWith(secretKey)로 서명 생성
     최종 JWT 문자열: compact()가 Header.Payload.Signature 형태로 합침
   - 코드에 자세한 설명이 있다.

22-5 Refresh Token 전략
   1. Refresh Token은 JWT로 발급한다.
   2. Refresh Token을 DB에 저장한다.
   3. Refresh Token을 HttpOnly Cookie로 브라우저에 내려준다.
   4. Access Token 만료 시 `/auth/refresh`에서 Refresh Token을 검증한다. (유저 페이지가 아님)
   5. 쿠키의 Refresh Token과 DB의 Refresh Token이 일치하면 새 Access Token을 발급한다.
   6. 로그아웃 시 DB의 Refresh Token을 삭제하고 쿠키도 삭제한다.
   (작업순서)
      1. RefreshToken Entity 만들기
       - Entity에서 @NoArgsConstructor는 매개변수 없는 생성자를 JPA가 DB값 읽어 필드에 넣음, 우리가 만든 생성자는 우리가 쓰기 위함
       - @PrePersist, @PreUpdate는 nullable안되도록 DB저장 시점에 now만들어 자동 저장
      2. RefreshTokenRepository 만들기
       - JpaRepository: Spring Data JPA가 제공하는 기본 Repository 인터페이스 (save, findBy...)
       - <RefreshToken, Long> 
       - 노트북 로그인: id = 1, userId = 5, token = A
         휴대폰 로그인: id = 2, userId = 5, token = B
         태블릿 로그인: id = 3, userId = 5, token = C 
         userId, tokenId(토큰 엔티티에서 @Id 고유값)을 잘 구분하자
      3. AuthService.login()에서 refreshToken도 생성&DB저장
      ---------------------------------------------------------------------------
      | 구분           | HttpOnly 쿠키             | 응답 데이터                     |
      ---------------------------------------------------------------------------
      | 전달 위치       | 응답 헤더의 `Set-Cookie`    | 응답 본문(JSON 등)              |
      | 브라우저 저장    | 브라우저가 자동 저장          | 자바스크립트가 받아서 직접 저장해야 함 |
      | 자바스크립트 접근 | 읽을 수 없음                | 읽을 수 있음                    |
      | 다음 요청 전송   | 브라우저가 자동 전송          | 자바스크립트가 헤더에 직접 넣어야 함   |
      | 주요 장점       | XSS로 토큰을 직접 훔치기 어려움 | 원하는 요청에만 직접 붙이기 쉬움     |
      ---------------------------------------------------------------------------
       - 리프레시토큰은 HttpOnly쿠키로, 억세스토큰은 응답데이터로 보냄
       - LoginResponse.java DTO만들기: 기존 로그인은 String 타입이므로 access, response 둘다 보낼 수 없으므로
         DTO를 하나 만들어서 묶어서 return
       - @AllArgsConstruct에 access = AccessLevel.PROTECTED옵션을 넣는 경우: 아무 클래스에서나 객체를 함부로 만들면 안 되지만, JPA 같은 프레임워크는 생성자를 사용해야 할 때
       - repository.save()는 왜 인자로 new entity를 받는가? -> JPA가 엔티티 자체를 토대로 DB에 저장해주기 때문
      - 프로바이더, 리포지토리, 엔티티, 프로퍼티스 등 여러 객체를 가져와 사용하므로 잘 구분하자
         사용자가 로그인 form 제출
         -> AuthController가 요청 받음
         -> AuthService.login() 호출
         -> UserRepository로 사용자 조회
         -> PasswordEncoder로 비밀번호 확인
         -> JwtTokenProvider로 Access Token, Refresh Token 생성
         -> RefreshTokenRepository로 Refresh Token DB 저장
         -> AuthService가 LoginResponse로 두 토큰 반환
         -> AuthController가 Refresh Token을 HttpOnly 쿠키로 내려줌
         -> Access Token은 응답 데이터로 전달
      4. AuthController.login()에서 refreshToken을 HttpOnly Cookie로 내려주기

22-7 JWT 인증 필터 만들기
   - 일단 기본적으로 JWT라는것은 증명서임 -> JWT를 사용하기 위한 필터를 하나 만들어서 스프링 시큐리티가 구성한
     필터체인에 추가해야 함 -> JwtAuthenticationFilter + 여러 기본 필터들을 통해 구성 
     * JWT: 사용자가 누구인지, 어떤 권한인지 담은 증명서
     * JwtAuthenticationFilter: 그 증명서를 꺼내서 검증하고 내용을 스프링 시큐리티용 Authentication 객체로
     변환해서 SecurityContext에 저장
     * 스프링 시큐리티 기본 필터들: 저장된 Authentication을 보고 로그인 여부와 권한을 판단해서 
     요청을 통과시키거나 막음
   - Spring 생태계에서 Spring Boot와 Spring Security는 각각 별도의 프로젝트·프레임워크다.
     내 프로젝트에서는 Spring Boot 플러그인을 적용해서 Gradle이 이 프로젝트를
     1. Spring Boot 방식으로 빌드·실행·패키징하게 했다.
     2. Spring Security 의존성을 추가해서 애플리케이션에서 보안 기능과 클래스들을 사용하게 했다.
   - 가드: 요청이나 기능에 접근 가능한지 막아주는 전체 개념
     필터: 그 가드 역할을 구현하는 방법 중 하나
     필터는 요청 통과 전에 검사, 가드는 요청을 하용해도 되는지 검사하는 규칙
   - 여러가지 세분화된 가드
     JWT 필터: 토큰 확인, 사용자 인증
     SecurityConfig: URL 접근 권한 확인
     @PreAuthorize: 메서드 실행 권한 확인
     서비스 로직: 작성자 본인인지 확인
   - JwtAuthenticationFilter 클래스 기본 구성
     extends OncePerRequestFilter: 요청당 한 번만 실행되게 해주는 필터 기본 클래스
     jwtTokenProvider: 토큰 생성하고 검증하는 도구(변수) -> 여기서는 토큰 정보를 읽어오도록 하는 역할
     doFilterInternal: 진짜 필터 로직이 들어가는 곳
     getAccessTokenFromCookie: 요청 쿠키에서 accessToken 찾아오는 보조 메소드
   - filterChain.doFilter(request, response); 는 다음에 연결된 필터나 컨트롤러로 넘어가 달라는 의미
     -> SecurityConfig에 필터 순서가 명시되어 있어야함
     -> SecurityConfig에 @RequiredArgsConstructor로 의존성 추가, addFilterBefore 해줌
   - 토큰은 type과 role이 있는데 헷갈리지 말 것
   - access token 검사 로직에 들어가는 코드 개념
     SecurityContextHolder: 현재 요청에 연결된 SecurityContext에 접근하는 입구
     getContext(): 보안 정보 보관 공간인 SecurityContext를 가져옴
     getAuthentication(): 그 보관 공간 안에 있는 인증 객체를 가져옴
     결국 스프링이 기본필터를 통해 자동으로 저장하는 보안 보관 공간에서 인증 객체를 가져오는 코드
     Authentication(인증객체) 안에는 이러한 많은 정보들이 들어가 있음
     ├── principal      // 사용자 정보
     ├── credentials    // 비밀번호 같은 인증 수단
     ├── authorities    // 권한 목록
     ├── details        // IP, 세션 ID 같은 추가 정보
     └── authenticated  // 인증 완료 여부
     결론: Authentication(인증객체) = user id + authorities(권한객체(들))
   - UsernamePasswordAuthenticationToken: 이름 때문에 아이디·비밀번호 로그인 전용처럼 보이지만,
     Spring Security에서 Authentication을 구현한 대표적인 클래스라서 JWT 인증 결과를 담을 때도 자주 씀
   - setDetails 부분은 관례적으로 추가함 -> 접속 IP 주소, 세션 IP
   - 언제 HttpServletRequest/Response를 써야 하는가? 
     DTO = 요청값을 담는 통
     request = 들어온 원본 정보 보기
     response = 나갈 응답을 세밀하게 만들기
     자동 처리 = DTO 바인딩, JSON 변환, 뷰 렌더링
     직접 처리 = 쿠키, 헤더, 상태코드, 파일, 필터
